# EASBot UI 代码注解规范 (Code Annotation Standard)

> **真值源**：本规范以 `src/` 下 187 个组件实现文件（`src/ui` 140 + `src/design-system` 47，排除 `__tests__` / stories / examples）、
> 123 个测试文件、79 个 story 文件的实际注解为唯一执行真值；
> 规范与实现冲突时**规范改**。
>
> **与其它规范的分工**（三者**不重复**）：
>
> | 关注点                          | 归属文档                                                | 本规范对应章节     |
> | ------------------------------- | ------------------------------------------------------- | ------------------ |
> | Biome 规则 / 格式化 / 类型安全  | [`code-quality.md`](./code-quality.md)                  | —                  |
> | 组件目录 / 命名 / 导出 / 封装   | [`component-standard.md`](./component-standard.md)      | —                  |
> | CSS 变量 / 主题 / Tailwind 类   | [`css-standard.md`](./css-standard.md)                  | —                  |
> | 测试文件头注解四段式 / 用例命名 | [`testing-guidelines.md`](./testing-guidelines.md) §3.1 | §3.2（仅组件库版） |
> | Story 文件头注解                | [`storybook-standard.md`](./storybook-standard.md)      | §3.3               |
>
> **历史基准**：v1.0.0 锁定 2026-10-31 数据，详见 §M+1。**规范条文本身不过期**，只有数据基准会过期。

## 概述 (Overview)

本规范定义**源代码内的注释与 JSDoc 注解**怎么写、怎么评审。它只管代码里的「注解」，不管 markdown 文档
（那由本 `spec/` 目录自身与 `README.md` 承担）。

**核心约束**：

- ✅ 注解描述**代码当前状况**：功能是什么、约束是什么、按什么步骤走
- ✅ 注解语言**中文正文 + 英文标识符**（技术术语保留英文）
- ✅ 组件实现文件顶部**必须**有头部块注释（存量豁免见 §M+2 H2）
- ✅ 导出符号**必须**有 JSDoc；props 字段**必须**有单行注解
- ✅ 复杂流程**必须**有核心步骤注解
- ❌ 禁止在注解里出现**人称称呼**（如具体人名 / 昵称）
- ❌ 禁止在注解里出现**决策编号引用**（如 `ADR 0112` / `决策 0073`）
- ❌ 禁止在注解里引用**外部文档 / 外部链接**
- ❌ 禁止在注解里写**过程性表述**（如「拍板」「用户要求」「用户反馈」）
- ❌ 禁止在注解里写**变更纪要**（如「2026-09-25 调整」「v0.5 重构后」）
- ❌ 禁止在注解里写**未来时态承诺**（如「将来会改成」「计划支持」）
- ❌ 禁止在注解里引用**本仓库 `spec/` 文档路径 / 章节号**

> ⚠️ **本规范的判定依据是「可复跑扫描」**：每条规则都配一条命令（§M），任何 Review 结论 **MUST** 基于扫描输出，不接受主观判断。
>
> 📌 **§2 的约束对象**：`src/` 下的 `.ts` / `.tsx` **源码注释与 JSDoc**，包括：文件头部块注释、符号级 JSDoc、
> 内联注释，以及**测试代码内的注释与 `describe()` / `it()` 标题字符串**。
> markdown 文档（`spec/` / `README.md`）内部的交叉引用**不在**本规范约束范围。

## 1. 注解四要素与总原则

### 1.1 注解四要素

一段合格的注解**按需**回答以下四类问题中的至少一类：

| 要素           | 回答的问题                                             | 典型内容                                                            |
| -------------- | ------------------------------------------------------ | ------------------------------------------------------------------- |
| **① 描述现状** | 这个文件 / 符号**是什么**、当前**处于什么状态**？      | 「Button 按钮组件 —— 触发一个操作或事件，如提交表单、打开对话框。」 |
| **② 功能**     | 它**做什么**、对外提供什么能力？                       | 「把一段（可能含 ANSI 的）多行文本按内容宽度做词感知换行。」        |
| **③ 约束**     | 使用它时**必须遵守什么**、边界在哪、有哪些**硬约定**？ | 「**加载时禁用点击**：`loading` 为真时按钮不可触发。」              |
| **④ 步骤**     | 复杂流程**按什么顺序**执行、关键决策点在哪？           | 「1. 判定移动端 → 2. 计算波纹坐标 → 3. 渲染波纹层。」               |

> 📌 **不是每条注解都要写满四要素**。单行 JSDoc 通常只回答 ① 或 ②；文件头部块注释通常覆盖 ②③④。

### 1.2 总原则：注解描述现状，不描述历史

| 原则                    | 说明                                                                                     |
| ----------------------- | ---------------------------------------------------------------------------------------- |
| **P1 现状优先**         | 注解写「代码现在是什么」，不写「代码曾经是什么」「为什么当初改成这样」。                 |
| **P2 约束可执行**       | 约束必须是读者能据此判断对错的（"加载时禁用点击"），不是感想（"这里写得挺好的"）。       |
| **P3 步骤可跟随**       | 步骤注解的编号必须与代码实际执行顺序一致；代码顺序变了，注解必须同步改。                 |
| **P4 注释解释不显然处** | 代码本身一眼能看懂的逻辑**不写注释**；注释写「为什么这样写」「什么条件下会走另一条路」。 |
| **P5 同步更新**         | 代码行为变化时，注解**必须**在同一提交内更新。                                           |

### 1.3 注解语言

- **正文用中文**（便于团队成员快速理解意图）。
- **技术术语保留英文**：类型名 / 函数名 / 组件名 / CSS 变量名 / HTML 属性名 一律英文原样。
- **标识符一律英文**（代码命名规范见 [`component-standard.md`](./component-standard.md) §2）。
- ⚠️ **不与 i18n 耦合**：注解里的中文是给开发者看的，**不是**用户文案。

### 1.4 三种注解载体

| 载体               | 位置                    | 适用对象                       | 强制程度                                           |
| ------------------ | ----------------------- | ------------------------------ | -------------------------------------------------- |
| **文件头部块注释** | 文件顶部（import 之前） | **所有** `.ts` / `.tsx` 源文件 | **新增文件 MUST**；存量文件 SHOULD（改动即补，H2） |
| **符号级 JSDoc**   | 导出符号 / 组件 正上方  | 所有**导出**符号 + props 字段  | MUST（导出符号）/ MUST（props 字段）               |
| **内联注释**       | 语句 / 代码块 内部      | 关键步骤、约束点、非常规写法   | SHOULD（复杂流程 / 反直觉逻辑）                    |

> 📌 **「改动即补」原则**（§M+2 H2）：**存量**文件的注解缺口不在全量回填范围内，但**任何一次触及某文件 / 符号的改动，必须顺手补齐该文件 / 符号的注解**。新增文件则一律 MUST 达标。

## 2. ⛔ 禁止内容清单（7 类）

> **这是本规范最核心的章节**。每类给出：禁止内容 → ❌ 反例 → ✅ 正例 → 扫描命令。

### 2.1 ⛔ 人称称呼

**禁止**在注解里出现任何**具体人的称呼、昵称、代号**。

| ❌ 反例                                         | ✅ 正例                                                |
| ----------------------------------------------- | ------------------------------------------------------ |
| `// 2026-09-25 老侯反馈：counts 字段彻底删除。` | `// counts 字段已删除：DB stats 是唯一真值源。`        |
| `// 老侯：edges 几百个肯定不对`                 | `// edges 数量必须截断：几百个节点会让上下文溢出。`    |
| `* 由小莫在 session 16 提出（决策 0073）`       | `* 公共契约升级为 NoteStatus（返回 6 字段诊断信息）。` |

**理由**：注解是代码的长期说明书。人员称呼在人员更替后会变成**无主语的历史噪音**，读者无法据此判断代码当前该怎么做。

> ⚠️ **例外**：**面向用户的界面文案示例**中的角色名（如演示文本里的人物名）属于**业务数据**而非注解表述，不受本条约束。

### 2.2 ⛔ 决策编号引用

**禁止**在注解里出现决策日志编号或决策日志路径（`ADR 0112` / `决策 0073` / `docs/decisions/xxx.md`）。

| ❌ 反例                                                   | ✅ 正例                                                 |
| --------------------------------------------------------- | ------------------------------------------------------- |
| `* 统一收敛到 Tool（ADR 0112 配套重构）`                  | `* Tool 定义统一收敛到单一入口；本模块只保留一处代理。` |
| `* @see docs/decisions/0116-buildin-tool.md`              | `* @see buildInTool（内置工具注册入口）`                |
| `describe('Select（决策 0106 配套 · 问题 3 修复）', ...)` | `describe('Select 组件', ...)`                          |

**理由**：决策编号是**文档体系**的锚点，不是**代码语义**的锚点。代码发布后编号可能因同号多文件冲突、合并、归档而失效；
更重要的是，**「为什么这么选」属于决策日志的职责**，代码注解只回答「现在是什么」。

> 📌 **正确做法**：把决策的**结论**（而非编号）写进注解。
> ❌ 反例的**问题不在于没写清楚**，而在于**写的是编号而非结论**。

### 2.3 ⛔ 外部文档 / 外部链接引用

**禁止**在注解里出现 `http://` / `https://` 链接，或指向外部仓库 / 外部站点。

| ❌ 反例                                                                                | ✅ 正例                                        |
| -------------------------------------------------------------------------------------- | ---------------------------------------------- |
| `* @see https://remedajs.com/docs/#mergeDeep`                                          | `* @see mergeDeep（深合并，递归合并嵌套对象）` |
| `* @see https://sw.kovidgoyal.net/kitty/keyboard-protocol/`                            | `* @see Key（Kitty 键盘协议解析结果）`         |
| `* @see {@link https://github.com/xxx/easbot-ui/blob/main/spec/component-standard.md}` | `* @see ComponentStandard`                     |

**理由**：外部链接会**腐化**（域名失效、页面移动、仓库改名），而代码注解是**构建期产物**——读者可能完全离线。
外链也是**供应链攻击面**：注解里的 URL 若指向恶意仓库，读者可能直接信任并访问。

#### 判定：三类外链形态

| #     | 形态                   | 特征                                     | 判定                    |
| ----- | ---------------------- | ---------------------------------------- | ----------------------- |
| **A** | **协议形态**           | 主机名是**占位符 / 模板变量 / 回环地址** | ✅ **自动放行**         |
| **B** | **真实外链（已登记）** | 指向真实外部站点                         | ✅ **放行，但须先登记** |
| **C** | **真实外链（未登记）** | 指向真实外部站点，但**不在登记表里**     | ❌ **违规**             |

> ✅ **形态 A 的判定是纯客观的**：主机名命中占位符特征（`localhost` / `127.0.0.1` / `<...>` / `${...}` / `*.example.com`）。
> **它不是「引用」，是「协议或占位符的字面写法」** —— 删掉它不会丢失任何语义。
>
> 📌 **形态 B 的正当用途**：上游规范 / 协议（RFC 8628、XDG Base Directory Spec）、实现参考 / 对标、本项目对外契约。
> 登记时 **MUST** 写明：URL + 位置 + 类别 + 理由 + 审核人 + 复核日期。**复核日期到期自动失效**。

### 2.4 ⛔ 过程性表述

**禁止**在注解里出现描述**协作过程**的表述。

| ❌ 反例                                                 | ✅ 正例                                               |
| ------------------------------------------------------- | ----------------------------------------------------- |
| `* 9 个变体名（短名，2026-07-15 拍板：去 prefix 前缀）` | `* 9 个变体名均为短名（不含前缀，由 cva 统一拼接）。` |
| `* - 不主动安装（用户要求"不再主动安装"）`              | `* - 不主动安装：缺失时直接报错，由使用方自行安装。`  |
| `* 2026-09-25 用户反馈：status 的计数应该一致`          | `* 计数与 db 统计保持一致：均动态查表。`              |

**理由**：「拍板」「用户要求」「用户反馈」记录的是**协作过程**，读者拿不到过程信息，只能看到一句没有主语的话。

#### 判定锚点：过程性 vs 业务语义

| 判定        | 锚点                                                                       |
| ----------- | -------------------------------------------------------------------------- |
| ❌ **违规** | 记录「谁在什么时候提了要求 / 做了决定」—— 去掉后不影响理解                 |
| ✅ **合法** | 描述**业务领域术语** / **协议字段语义** / **事件类型枚举** —— 去掉会丢语义 |

**合法豁免的 3 类典型形态**：schema 字段语义（`/** 用户反馈内容 */`）、协议层分类概念、事件类型枚举。

### 2.5 ⛔ 变更纪要

**禁止**在注解里写**变更历史**（版本号 + 日期 + 改了什么）。

| ❌ 反例                                        | ✅ 正例                                        |
| ---------------------------------------------- | ---------------------------------------------- |
| `* v0.5.1 重构（决策 0073）：返回 NoteStatus`  | `* 返回 NoteStatus：包含 6 个诊断字段。`       |
| `* 演进历史：session 16 (v0.4)：纯算法 status` | `* 计数来自数据库真实 row count，不做缓存。`   |
| `* 2026-09-25 调整：把 counts 字段彻底删除`    | `* counts 字段已删除：DB stats 是唯一真值源。` |

**理由**：变更历史由 `git log` 承载。注解里的「v0.5.1 重构」既无上下文，也会让每次升级都**继续追加**变成噪音。

> 📌 **区分点**：`向后兼容` 这类**当前仍在生效的约束**要写（它描述现状），但**不要**带版本号与日期。

### 2.6 ⛔ 未来时态承诺

**禁止**在注解里承诺**尚未实现**的行为。

| ❌ 反例                                    | ✅ 正例                                      |
| ------------------------------------------ | -------------------------------------------- |
| `* 将来会支持流式输出，目前先返回完整结果` | `* 当前一次性返回完整结果，不支持流式输出。` |
| `* 计划在 v0.4 增加缓存机制`               | `* 无缓存：每次调用都重新计算。`             |
| `* TODO: 后续改为异步`                     | `// TODO(#ISSUE-123): [PERF] 改为异步`       |

**理由**：未实现的行为不是代码的现状。承诺型注解一旦落空就成了**误导**。

### 2.7 ⛔ 本仓库 `spec/` 文档路径 / 章节号引用

**禁止**在注解里引用 `spec/` 下的规范文档（**路径与章节号两种形态都算**）。

| ❌ 反例                                                | ✅ 正例                                                  |
| ------------------------------------------------------ | -------------------------------------------------------- |
| `* 本组件遵循 spec/component-standard.md §3.1`         | `* 组件必须用 React.forwardRef 封装并设置 displayName。` |
| `* 这里改为按 [spec/css-standard.md](./x.md)`          | `* 颜色一律走 CSS 变量，不硬编码色值。`                  |
| `* 级别依据（spec §5.1）：WARN 的语义是「降级但继续」` | `* 级别依据：WARN 的语义是「降级但继续，功能受影响」。`  |

**理由**：与 §2.2 同源 —— `spec/` 文件路径与章节号是**项目文档体系**的锚点，会随文档重命名 / 合并 / 删除而失效；
且规则本身应**内联在代码里**（代码是执行真值，规范是描述）。

> 📌 **整改时 MUST 替换为规则内容**（把 `spec/css-standard.md §3.1` 换成「颜色一律走 CSS 变量」），
> **不能简单删除** —— 删除会丢失语义，让读者失去约束依据。
>
> ✅ **合法例外**：引用**仓库内源码文件路径**（如 `src/utils/classnames.ts`）—— 这是**同一代码库内的稳定锚点**。

## 3. 分类型头部注解模板（3 类）

> **判定顺序**：按文件**职责**选唯一一类模板，从上往下匹配，先命中先适用。
>
> | #   | 类型           | 判定特征                                                | 模板小节 |
> | --- | -------------- | ------------------------------------------------------- | -------- |
> | 1   | **组件实现**   | `src/ui/<component>/<component>.tsx`（导出 React 组件） | §3.1     |
> | 2   | **测试文件**   | `*.test.tsx`                                            | §3.2     |
> | 3   | **Story 文件** | `*.stories.tsx`                                         | §3.3     |

### 3.1 组件实现模板

**适用**：`src/ui/<component>/<component>.tsx`。

**必填**：`@description`（做什么）+ 特性列表（有什么能力）+ 可选 `@example`。

**骨架**：

```tsx
/**
 * <Component> <中文名称>组件
 *
 * @description
 * <一句话定位：这个组件做什么>
 *
 * 特性：
 * 1. <能力一>
 * 2. <能力二>
 * 3. <无障碍>
 */
```

**正例**（取自 [`src/ui/button/button.tsx:1-19`](../src/ui/button/button.tsx)）：

```tsx
/**
 * Button 按钮组件
 *
 * @description
 * 用于触发一个操作或事件，如提交表单、打开对话框、取消操作或执行删除操作。
 *
 * 特性：
 * 1. 样式变体 - 支持多种预设样式
 * 2. 尺寸变化 - 支持不同大小按钮
 * 3. 状态反馈 - 支持加载、禁用状态
 * 4. 图标支持 - 支持左右图标配置
 * 5. 移动适配：
 *    - 优化触摸区域
 *    - 波纹反馈效果
 *    - 手势支持
 *    - 压力感应
 *    - 触觉反馈
 * 6. 无障碍 - 支持键盘导航和屏幕阅读
 */
```

**符号级 JSDoc**（组件本体）：

````tsx
/**
 * Button 组件实现
 *
 * @param props - 按钮属性
 * @param ref - 按钮引用
 * @returns React 组件
 *
 * @example
 * ```tsx
 * <Button>点击我</Button>
 * <Button leftIcon={<Mail />}>发送邮件</Button>
 * <Button loading>提交中</Button>
 * ```
 */
````

**正例**：[`src/ui/button/button.tsx:110-139`](../src/ui/button/button.tsx)

> 📌 **要点**：能力列表用**编号 + 短横线**，每项一行；复杂能力用二级缩进展开子项。

### 3.2 测试文件模板

## 4. 符号级 JSDoc 标签最小集

| 标签       | 何时必填                                    | 写法要求                                |
| ---------- | ------------------------------------------- | --------------------------------------- |
| `@param`   | 函数有参数时 **MUST**；可选参数也 MUST 标注 | 格式 `@param name - 说明`（破折号必写） |
| `@returns` | 函数有返回值时 **MUST**                     | 说明**返回什么**，不重复函数名          |
| `@throws`  | 函数会抛出**业务异常**时 MUST               | 格式 `@throws <ErrorName> - <触发条件>` |
| `@example` | 公共 API SHOULD 有                          | 代码块语言用 `tsx` / `ts`               |
| `@see`     | 有强关联的其它符号时 SHOULD                 | **只指向本仓库符号**（§4.1）            |

**不强制 / 禁止使用**：`@author` `@version` `@since` `@module` `@internal` `@license` `@deprecated`。

> 📌 **组件库语境下 `@see` 的合法目标**：`@see DialogPrimitive.Content（Radix 原始实现）` /
> `@see cn（类名合并工具）` / `@see src/utils/classnames.ts`。
> ⛔ **禁止**指向外部 URL、决策日志、`spec/` 文档路径。

## 5. 核心步骤注解规范

### 5.1 何时必须写步骤注解

| 场景                                          | 强制程度 |
| --------------------------------------------- | -------- |
| 函数 / 回调**超过 20 行**且含分支决策         | **MUST** |
| 流程有**明确的阶段划分**（≥ 3 个阶段）        | **MUST** |
| 存在**顺序敏感**的操作（先 A 后 B，颠倒会错） | **MUST** |
| 有**非直觉的兜底 / 降级**分支                 | **MUST** |
| 简单线性函数（< 10 行）                       | 不需要   |

### 5.2 三种形态

**形态 A —— 编号序列**（用于有明确先后顺序的流程）：

```ts
/**
 * 处理一次触摸交互。
 *
 * 1. 判定是否移动端 —— 非移动端直接返回。
 * 2. 计算波纹坐标 —— 取触点相对按钮的位置。
 * 3. 渲染波纹层 —— 300ms 后自动移除。
 */
```

**形态 B —— 阶段分隔**（用于长函数，标注当前处于哪个阶段）：

```ts
// ── 阶段 1：计算坐标 ──────────────────────────────────────
const x = clientX - rect.left;

// ── 阶段 2：写入波纹状态 ──────────────────────────────────
setRipples((prev) => [...prev, { x, y, id }]);
```

**形态 C —— 关键决策点**（用于分支密集、每条路径语义不同的逻辑）：

```ts
// 禁用态：不触发波纹，也不调用外部回调
if (isDisabled) return;
```

### 5.3 步骤注解的内容要求

| 要求                                 | 反例                         | 正例                                                   |
| ------------------------------------ | ---------------------------- | ------------------------------------------------------ |
| **步骤与代码顺序一致**               | 注解写 3 步，代码有 5 个分支 | 编号覆盖全部阶段                                       |
| **每步说清"做什么"，不重复代码字面** | `// 1. 调用 createRipple`    | `// 1. 计算波纹坐标 —— 取触点相对按钮的位置`           |
| **标注非直觉的"为什么"**             | `// 2. 这里要转一下`         | `// 2. 先取缓存再落库 —— 保证并发下只有一条初始化日志` |
| **不写"做什么"的复述**               | `// 遍历数组`                | （删除）                                               |

## 6. 内联注释规范

### 6.1 写法

```ts
// 中文说明，句末不加句号（单行短注释）
const isMobile = React.useMemo(() => { ... }, []);
```

- 单行短注释用 `//`，多行说明用 `/** */`。
- 注释写在**被说明代码的上一行**（不写行尾），除非该行过长必须行尾。
- 注释里的标识符用**反引号**包裹：`` `isMobile` ``。

### 6.2 什么不写

| 不写                                           | 理由                                                     |
| ---------------------------------------------- | -------------------------------------------------------- |
| 复述代码字面（`// 遍历数组` / `// 返回 true`） | 代码本身已表达，无信息量                                 |
| 逐行翻译代码                                   | 增加维护成本，代码变了注释就过时                         |
| 被注释掉的代码                                 | 由 `git log` 承载历史；用版本控制删除                    |
| 「这里是 hack」而无原因                        | 约束不完整 —— 要写**为什么临时**、**什么条件下会被替换** |

### 6.3 TODO / FIXME / HACK

格式固定为 `TODO(#ISSUE-N): [TAG] 描述`，**必须**带 `ISSUE-` 前缀与 `[TAG]`。

```ts
// TODO(#ISSUE-123): [FEAT] 添加 size="mobile" 尺寸变体 - 待补齐 mobile 尺寸档位
// FIXME(#ISSUE-456): [BUG] 移动端长按阈值偏大 - 边界条件未覆盖
// HACK(#ISSUE-789): [REFACTOR] 临时硬编码波纹时长 - 待抽为可配置项
```

> 📌 **TAG 取值**：`FEAT`（新功能）/ `BUG`（缺陷）/ `PERF`（性能）/ `REFACTOR`（重构）/ `STYLE`（样式）/ `DOC`（文档）。
>
> ⚠️ **TODO 不是未来承诺的替代品** —— 它必须指向一个**可追踪的 Issue**，而不是一句许诺。

## M+4. 模块检查清单

> **目的**：新增 / 评审组件时的**自查**清单（不是任务列表，是合规性自检表）。

### 新增组件时

- [ ] 文件头有块注释（`@description` + 能力列表）
- [ ] 组件本体有 JSDoc（`@param` / `@returns` / `@example`）
- [ ] props 每个字段有单行 JSDoc，有默认值的带 `@default`
- [ ] 每个子组件有单行职责 JSDoc
- [ ] 复杂回调（> 20 行 + 分支）有编号步骤 / 阶段分隔 / 关键决策点注释之一
- [ ] 无 ⛔ 7 类禁止内容（维度 ① ~ ⑦ 已跑）
- [ ] TODO 全部符合 `TODO(#ISSUE-N): [TAG]` 格式

### 评审组件时

- [ ] 维度 ① ~ ⑨ 已全跑（一次跑全库）
- [ ] 改动的文件注解已同步更新（§1.2 P5）
- [ ] 注解语言为中文正文 + 英文标识符
